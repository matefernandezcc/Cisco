2) Analice el tráfico cursado, graficando la comunicación de tramas (intercambio de tramas que encapsulan los segmentos que representan la comunicación orientada a la conexión) y verifique lo siguiente:
a) Establecimiento de conexión TCP:
(1) ¿Cuántos segmentos se emplean para establecer y liberar la comunicación?

• Para establecer la comunicación: Se emplean exactamente 3 segmentos a través del proceso normalizado denominado Three-Way Handshake (Apretón de manos de 3 vías):

  1. Segmento 1 (Cliente → Servidor): [SYN] Solicitud de sincronización y anuncio de parámetros iniciales.
  2. Segmento 3 (Servidor → Cliente): [SYN, ACK] Acuse de recibo del SYN del cliente y anuncio del SYN propio del servidor.
  3. Segmento 4 (Cliente → Servidor): [ACK] Acuse de recibo del SYN del servidor. La conexión pasa al estado ESTABLISHED.

• Para liberar la comunicación: Se emplean 4 segmentos (o 3 si se combinan FIN y ACK en piggybacking) mediante el proceso Four-Way Handshake de desconexión ordenada, debido a que TCP es Full Duplex y cada sentido de transmisión debe cerrarse de manera independiente:

  1. Segmento 11 (Servidor → Cliente): [FIN, ACK] El servidor anuncia que no transmitirá más datos (cierre de Tx servidor).
  2. Segmento 12 (Cliente → Servidor): [ACK] El cliente confirma la recepción del FIN del servidor.
  3. Segmento 13 (Cliente → Servidor): [FIN, ACK] El cliente finaliza su transmisión y cierra su sentido (cierre de Tx cliente).
  4. Segmento 14 (Servidor → Cliente): [ACK] El servidor confirma el FIN del cliente. La conexión queda totalmente cerrada (CLOSED).
(2) Para el establecimiento de la conexión analice el paso a paso:
(a) Window Size:
1. Cliente → Servidor (SYN): ¿Incluye el campo Window Size = W1? ¿qué significa y para qué servicio se emplea?

Sí, incluye explícitamente el campo Window Size, con un valor medido en la captura de W1 = 64240 bytes (con factor de escala Window Scale = 256 negociado en las opciones TCP).

Significado: Representa el tamaño de la ventana de recepción (Receive Window, rwnd) que el cliente ofrece al servidor en ese instante. Indica la cantidad de bytes que el cliente es capaz de almacenar en su buffer de recepción sin que se produzca pérdida por saturación.

Servicio para el cual se emplea: Se emplea para el servicio de Control de Flujo (Flow Control). Su función primordial es evitar que un emisor rápido sobrecargue y desborde el buffer de memoria del receptor lento, garantizando que el transmisor nunca tenga en tránsito más datos sin confirmar que los permitidos por la ventana anunciada.

2. Servidor → Cliente (SYN-ACK): ¿Incluye Window Size = W1 o W2? ¿por qué?

Incluye un valor independiente W2 (en nuestra captura: W2 = 26883 bytes, con opción Window Scale = 128).

Justificación técnica: Porque TCP es una conexión completamente Full Duplex (bidireccional simétrica). Ambos extremos disponen de recursos de memoria, sockets y buffers de recepción independientes asignados por sus respectivos sistemas operativos. El servidor debe anunciar al cliente la capacidad disponible en su propio buffer de recepción (W2), el cual no tiene relación alguna con el buffer asignado por el cliente (W1). Cada sentido de transmisión posee su propio control de flujo desacoplado.

3. Cliente → Servidor (ACK): ¿Confirma el ISN del servidor?

Sí, confirma explícitamente el ISN del servidor.

En el segmento SYN-ACK (Trama 3), el servidor anunció su Número de Secuencia Inicial ISN_servidor = y = 1302559821 (valor relativo 0). En el protocolo TCP, el flag de control SYN consume virtualmente 1 unidad de espacio de numeración de secuencia (a pesar de no transportar datos de aplicación). (4) ¿en qué se asemejan y en qué se diferencian de la secuencia analizada para el three-way handshake?

• Semejanzas:

  • Ambos procesos utilizan la misma estructura de cabecera TCP estandarizada con campos de 32 bits de Sequence Number y Acknowledgment Number.
  • En ambos casos el campo Ack especifica el próximo número de secuencia que el receptor espera recibir del emisor.
  • En ambos casos cada segmento actualiza el campo Window Size informando el espacio de buffer libre del emisor para el control de flujo continuo.

• Diferencias:

  • Flags de control: En el handshake intervienen los flags de sincronización SYN y SYN-ACK. En la transferencia se utilizan ACK y PSH (Push).
  • Carga útil (Payload / Len): En el handshake los segmentos no transportan datos de aplicación (Len = 0 bytes). En la transferencia los segmentos transportan los bytes reales del protocolo de aplicación (Len > 0 bytes).
  • Incremento de Sequence Number: En el handshake, el flag SYN consume de manera ficticia 1 unidad de secuencia (el ACK responde con $ISN + 1$). En la transferencia, el número de secuencia se incrementa estrictamente en función de la cantidad de bytes reales transmitidos: $Seq_{next} = Seq_{actual} + Len$.
  • Opciones de negociación: Las opciones TCP avanzadas (MSS, Window Scale, SACK-Permitted) solo se negocian en los segmentos SYN del handshake. Durante la transferencia de datos ya no se renegocian estas capacidades.
d) ¿Qué servicios proporciona TCP en el nivel de transporte?

TCP proporciona un conjunto integral de servicios orientados a la conexión:

  1. (1) ¿Ordenamiento y reensamble? SÍ. TCP asigna un número de secuencia correlativo a cada byte individual. Si los paquetes IP viajan por rutas distintas en Internet y llegan desordenados, el receptor los retiene en su buffer de reensamble y los ordena matemáticamente antes de entregarlos de forma secuencial y transparente a la capa de aplicación.
  2. (2) ¿Fiabilidad? SÍ. Brinda entrega confiable extremo a extremo (Reliable Data Transfer). Garantiza que el flujo de datos entregado a la aplicación destino sea una réplica exacta, completa y no corrompida de lo transmitido, recuperando pérdidas y descartando duplicados mediante el mecanismo PAR (Positive Acknowledgment with Retransmission).
  3. (3) ¿Control de errores - Reconocimientos y retransmisiones? SÍ. Posee un campo Checksum de 16 bits para detectar corrupción de bits (los segmentos corruptos se descartan). Implementa reconocimientos acumulativos (ACKs) y selectivos (SACK). Si el emisor no recibe el ACK antes de que expire el temporizador RTO (Retransmission Timeout), o si recibe 3 ACKs duplicados (Fast Retransmit), retransmite el segmento de inmediato. En nuestra captura se observó la retransmisión del SYN a los 1.007 segundos.
  4. (4) ¿Control de flujo? SÍ. Implementa el algoritmo de Ventana Deslizante (Sliding Window). El receptor notifica en cada segmento el tamaño libre de su buffer mediante el campo Window Size. Si la ventana llega a cero (Zero Window), el emisor frena el envío de datos hasta recibir una actualización de ventana (Window Update), evitando el colapso del buffer del receptor.
  5. (5) ¿Multiplexación? SÍ. Permite que múltiples aplicaciones y procesos compartan concurrentemente la misma interfaz física y la misma dirección IP. Se logra combinando las direcciones IP con los números de puerto origen y destino de 16 bits (puertos efímeros y conocidos), formando sockets independientes.
  6. (6) ¿Conexión Full Duplex? SÍ. Permite la transferencia simultánea y bidireccional de datos en ambos sentidos a través del mismo canal. Cada sentido posee su propia numeración de secuencia y su propia ventana de flujo. Además, TCP utiliza piggybacking, aprovechando los segmentos con datos salientes para transportar los acuses de recibo de los datos recibidos.

2) Analice el tráfico cursado, graficando la comunicación de tramas y verifique lo siguiente:
a) Si UDP proporciona los siguientes servicios en el nivel de transporte:
  1. (1) ¿Conexión? NO. UDP es un protocolo no orientado a la conexión (Connectionless). No existe una fase previa de handshake para acordar parámetros ni una fase posterior de cierre o liberación. Cada datagrama se transmite de forma totalmente autónoma e independiente hacia la dirección IP y puerto destino.
  2. (2) ¿Fiabilidad? NO. Ofrece un servicio de entrega de mejor esfuerzo (Best-Effort). No garantiza que el datagrama llegue a destino, no implementa acuses de recibo (ACKs), no detecta pérdida de paquetes, no retransmite automáticamente ni previene la duplicación de datagramas. La fiabilidad, si se requiere, debe ser programada íntegramente en la capa de aplicación.
  3. (3) ¿Control de Flujo? NO. El encabezado UDP no posee campo de ventana (Window Size) ni ningún mecanismo de retroalimentación de flujo. UDP envía los datagramas a la tasa que la aplicación se los entrega; si el buffer del receptor o de los routers intermediarios se satura, los datagramas simplemente se descartan.
  4. (4) ¿Control de errores? PARCIAL.
    • Provee detección de corrupción de bits mediante el campo Checksum de 16 bits (en nuestra captura: 0xd12b y 0xcba4), que cubre el pseudoencabezado IP, el encabezado UDP y los datos.
    • Sin embargo, NO posee recuperación ni control de errores por pérdidas: si el receptor detecta un checksum inválido, descarta el datagrama silenciosamente sin notificar al emisor ni solicitar retransmisión. En IPv4 el uso del checksum es opcional, mientras que en IPv6 es obligatorio.
  5. (5) ¿Multiplexación? SÍ. Al igual que TCP, UDP brinda multiplexación y demultiplexación en Capa 4 a través de los campos de 16 bits Source Port (puerto efímero del cliente 56459) y Destination Port (puerto conocido 53 de DNS), permitiendo que múltiples procesos de red utilicen simultáneamente la misma pila de red IP sin colisiones.

3) Realice el siguiente cálculo para determinar el encapsulamiento de un segmento UDP y otro TCP:
DHCP – HTTP – HTTPS – FTP – DNS
a) Estudie los procesos / servicios de segmentación, ordenamiento y reensamble; multiplexación; encapsulamiento; conexión; confiabilidad; control de flujo y control de errores que el protocolo TCP o UDP le brindan a cada protocolo de aplicación, en cada caso.

A continuación se fundamenta la elección del protocolo de transporte (TCP o UDP) y el rol de cada proceso para las 5 aplicaciones requeridas:

  • 1. DHCP (Dynamic Host Configuration Protocol) → Utiliza UDP (Puertos 67 Servidor / 68 Cliente):
    Justificación: Cuando un host cliente se inicia en la red, carece de dirección IP asignada, no conoce la máscara de subred ni el gateway. Por ende, es matemáticamente imposible establecer una conexión TCP (que exige direcciones IP unicast en emisor y receptor para el handshake). DHCP requiere datagramas difundidos por Broadcast (IP destino 255.255.255.255 y MAC destino ff:ff:ff:ff:ff:ff) mediante transacciones cortas e independientes (Discover, Offer, Request, ACK). UDP no añade sobrecarga de conexión ni control de flujo innecesario.
  • 2. HTTP (Hypertext Transfer Protocol) → Utiliza TCP (Puerto 80):
    Justificación: La transferencia de documentos web (HTML, JavaScript, CSS, imágenes) exige cero tolerancia a pérdidas o corrupción de bits; la pérdida de una sola etiqueta o carácter corrompería la página o el script. TCP brinda entrega confiable, ordenamiento estricto y control de flujo adaptado a la memoria del navegador.
  • 3. HTTPS (HTTP Secure over TLS/SSL) → Utiliza TCP (Puerto 443):
    Justificación: La capa criptográfica TLS/SSL opera como una máquina de estados secuencial basada en registros cifrados en bloques o streams continuos. Si un solo segmento se perdiera, duplicara o alterara su orden, el receptor no podría descifrar los bloques posteriores debido a la desincronización de los vectores de inicialización (IV) y números de secuencia de los MACs criptográficos. Exige fiabilidad absoluta e incondicional en Capa 4.
  • 4. FTP (File Transfer Protocol) → Utiliza TCP (Puertos 21 Control / 20 o Dinámico Datos):
    Justificación: FTP implementa una arquitectura de dos conexiones paralelas: una conexión de control (puerto 21) para autenticación y comandos de estado, y una conexión de datos (puerto 20 o dinámico negociado en PASV) para transferir archivos binarios completos. Cualquier pérdida de bytes corrompería irreversiblemente los archivos descargados o subidos, haciendo indispensable la garantía de confiabilidad y reordenamiento de TCP.
  • 5. DNS (Domain Name System) → Utiliza UDP (Puerto 53) primario / TCP (Puerto 53) secundario:
    Justificación:
    • Uso primario de UDP: Las consultas de nombres constan de un único mensaje de pregunta y un único mensaje de respuesta. Utilizar TCP requeriría 3 paquetes de handshake + 4 de teardown para resolver un nombre, triplicando la latencia y sobrecargando masivamente los servidores raíz y TLD de Internet.
    • Uso de TCP: Se utiliza cuando la respuesta excede los 512 bytes del datagrama UDP tradicional (o el buffer negociado en EDNS0) y el servidor activa el bit TC (Truncated), forzando al cliente a reintentar por TCP. También se emplea obligatoriamente para transferencias de zona completa (Zone Transfers - AXFR/IXFR) entre servidores primarios y secundarios, donde se requiere transferir bases de datos íntegras sin errores.

Conclusión Comparativa del Encapsulamiento:
El encabezado UDP introduce una sobrecarga mínima constante de 8 bytes, lo que representa una reducción del 60% en sobrecarga de transporte frente a los 20 bytes mínimos de TCP (o hasta 60 bytes cuando TCP incluye opciones de sincronización como MSS, Window Scale, SACK y Timestamps). Esto optimiza la velocidad y latencia en transacciones cortas (DNS, DHCP, streaming de audio/video en tiempo real), mientras que TCP justifica sus 20 bytes adicionales aportando control de congestión, control de flujo, ordenamiento y entrega confiable garantizada.
