10) ¿Cuántos hosts puede haber en la red como máximo?
Para una máscara /24, la cantidad de bits para host es \(h = 32 - 24 = 8\).
Cantidad máxima de hosts asignables = \(2^h - 2 = 2^8 - 2 = 256 - 2 =\) 254 hosts.
(Se descuentan la dirección de red 192.168.0.0 y la dirección de broadcast 192.168.0.255).

12) ¿Es una red que detecta colisiones? En caso afirmativo, ¿Cuántos dominios de colisión tiene?
El protocolo IEEE 802.3 base posee detección de colisiones mediante CSMA/CD. Sin embargo, en esta red Ethernet conmutada que opera en Full-Duplex mediante un Switch, cada puerto del switch forma un enlace punto a punto dedicado, eliminando físicamente las colisiones.
Cantidad de dominios de colisión: La red tiene tantos dominios de colisión como puertos conmutados activos posea el switch (1 dominio de colisión por cada puerto con conexión activa).
13) ¿Es una red que previene colisiones? En caso afirmativo, ¿Qué problemas resuelve CSMA/CA que no resuelve CSMA/CD?
En la interfaz inalámbrica IEEE 802.11 sí es una red que previene colisiones mediante CSMA/CA.
Problemas que resuelve: En el medio inalámbrico (aire), una estación que transmite satura su propio receptor, impidiéndole detectar colisiones mientras transmite (CSMA/CD no es viable). Además, resuelve el problema del nodo oculto (Hidden Node Problem) —donde dos estaciones fuera de su rango mutuo transmiten simultáneamente al mismo punto de acceso— y el problema del nodo expuesto, utilizando ranuras de tiempo de espera (IFS), backoff aleatorio e intercambios opcionales de tramas de control RTS (Request to Send) y CTS (Clear to Send).
14) ¿Es una red que utiliza broadcast de direcciones MAC? En caso afirmativo, ¿Cuántos dominios de broadcast tiene? ¿Qué protocolos en entorno LAN/WLAN utilizan broadcast de capa 2 para funcionar?
Sí, utiliza broadcast de Capa 2 a través de la dirección MAC de difusión FF:FF:FF:FF:FF:FF.
Dominios de broadcast: Posee 1 único dominio de broadcast, ya que todos los puertos del switch/router hogareño integran la misma LAN sin enrutamiento interno ni segmentación en VLANs.
Protocolos que utilizan broadcast de Capa 2:
  • ARP (Address Resolution Protocol): Mediante el ARP Request enviado a broadcast para descubrir la MAC de una IP.
  • DHCP (Dynamic Host Configuration Protocol): En los mensajes iniciales DHCP Discover y DHCP Request cuando el cliente aún no tiene IP configurada.
  • Wake-on-LAN (WoL): Mediante el "Magic Packet" enviado a broadcast.
15) En una LAN ¿cómo se puede segmentar un dominio de colisión?
Un dominio de colisión se segmenta incorporando dispositivos de Capa 2, principalmente Switches (conmutadores) o Bridges (puentes). Cada puerto de un switch crea un dominio de colisión aislado e independiente.
16) En una LAN ¿cómo se puede segmentar un dominio de broadcast?
Un dominio de broadcast se segmenta mediante:
  • Dispositivos de Capa 3: Routers (enrutadores) o switches de Capa 3 (Multilayer Switches), los cuales no reenvían tramas de broadcast de Capa 2 entre sus interfaces.
  • A nivel lógico en switches de Capa 2: Mediante la creación de VLANs (Virtual Local Area Networks - IEEE 802.1Q), aislando el tráfico de difusión dentro de cada VLAN.
17) ¿Esta red emplea direccionamiento IP estático o dinámico? ¿Qué protocolo se utiliza para asignación dinámica de direcciones IP y cuántas PDU se intercambian entre el cliente y el servidor?
Emplea direccionamiento IP dinámico.
El protocolo utilizado es DHCP (Dynamic Host Configuration Protocol), operando sobre UDP (puerto 68 cliente, puerto 67 servidor).
Se intercambian un total de 4 PDUs durante el proceso de concesión (secuencia D.O.R.A.):
  1. DHCP Discover: El cliente busca servidores DHCP disponibles (Broadcast L2/L3).
  2. DHCP Offer: El servidor ofrece una dirección IP y parámetros de configuración (Unicast o Broadcast).
  3. DHCP Request: El cliente solicita formalmente la concesión de la IP ofrecida (Broadcast).
  4. DHCP ACK (Acknowledge): El servidor confirma la asignación y los tiempos de concesión (Lease).

b. Análisis de una trama Ethernet (Captura de Ping al Gateway)

Archivo de captura generado: wireshark/TL5/capturas/b_ping_gateway.pcapng (8 paquetes ICMP capturados correspondientes a 4 solicitudes de eco y 4 respuestas con el Gateway 192.168.0.1).
1) ¿Cuáles son los campos de la trama? ¿Qué valores tiene cada campo y cuál es su significado?
Analizando la trama Nº 1 (Echo Request enviado al Gateway):
  • Preámbulo y SFD: 7 bytes de preámbulo (0xAA...) y 1 byte de delimitador de inicio de trama SFD (0xAB). Operan en Capa 1 Física para sincronización de reloj del receptor. No son capturados por Wireshark ya que la NIC los procesa en hardware.
  • Destination MAC (Dirección MAC Destino): cc:32:e5:18:1d:fc (6 bytes). Identifica la placa física del receptor inmediato en la LAN (Router / Gateway TP-Link).
  • Source MAC (Dirección MAC Origen): b4:2e:99:56:09:3d (6 bytes). Identifica la placa de red de la estación transmisora (PC Gigabyte).
  • EtherType (Tipo de Protocolo): 0x0800 (2 bytes). Indica que el protocolo de capa superior encapsulado dentro del payload es IPv4.
  • Data / Payload (Carga Útil): 60 bytes en esta trama. Contiene el datagrama IPv4 completo (20 bytes cabecera IPv4 + 8 bytes cabecera ICMP + 32 bytes de datos ICMP).
  • FCS (Frame Check Sequence): 4 bytes. Secuencia de comprobación de trama mediante CRC-32 para detección de errores de transmisión.
2) ¿Qué tamaño tiene el encabezado de la trama y cuáles son sus campos?
El encabezado de la trama Ethernet II tiene un tamaño fijo de 14 bytes, compuesto por:
  • MAC Destino: 6 bytes
  • MAC Origen: 6 bytes
  • EtherType: 2 bytes
3) ¿Qué tamaño tiene la cola de su trama? ¿Qué campo sirve para detectar errores y cuál es su valor?
La cola de la trama tiene un tamaño de 4 bytes.
El campo destinado a la detección de errores es el FCS (Frame Check Sequence), calculado con un código de redundancia cíclica de 32 bits (CRC-32).
Nota técnica: En sistemas Windows, los controladores de la tarjeta de red (NIC) verifican el FCS en hardware y lo descartan antes de transferir la trama a la pila del sistema operativo, por lo cual Wireshark habitualmente no muestra el campo FCS en la captura. Su valor estandarizado es un polinomio CRC-32 de 4 bytes.
4) ¿Cuántos bytes corresponden a los datos? ¿Este campo es de tamaño fijo o variable? En este nivel ¿el campo de datos tiene una longitud mínima, máxima o no está especificado por su estándar?
En la trama capturada corresponden 60 bytes a los datos (datagrama IP).
El campo es de tamaño variable.
En el estándar IEEE 802.3 / Ethernet II:
  • Longitud mínima: 46 bytes. Si los datos superiores tienen menor tamaño, se añade un campo de relleno (Padding) para garantizar que la trama alcance los 64 bytes mínimos exigidos por el mecanismo de detección de colisiones de Ethernet (14B cabecera + 46B datos + 4B FCS = 64B).
  • Longitud máxima: 1500 bytes, definida por la Unidad Máxima de Transferencia (MTU) estándar de Ethernet.
5) Revisando nuevamente la trama Ethernet ¿qué campos se corresponden con los especificados en IEEE 802.2 y cuáles a IEEE 802.3?
  • IEEE 802.3: Define la subcapa MAC: Preámbulo, SFD, Dirección MAC Destino, Dirección MAC Origen, campo Longitud y FCS.
  • IEEE 802.2: Define la subcapa LLC (Logical Link Control), añadiendo encabezados adicionales como DSAP (Destination Service Access Point), SSAP (Source Service Access Point) y Control.
  • Análisis de la trama capturada: La trama capturada sigue el formato estándar Ethernet II (DIX), en el cual el campo de 2 bytes posterior a las MACs tiene un valor \(\ge 0x0600\) (aquí 0x0800), funcionando como EtherType. Por lo tanto, no contiene cabecera IEEE 802.2 LLC, multiplexando directamente hacia la Capa de Red.
6) ¿Qué protocolos de nivel 3 (TCP/IP) se encapsularon en las tramas?
Se encapsuló IPv4 (identificado por EtherType 0x0800) y, dentro del datagrama IP, el protocolo de control de nivel 3 ICMP (Internet Control Message Protocol, identificado por el campo Protocol con valor 1 en la cabecera IP).
7) ¿Qué protocolos de nivel 4 y 5 (TCP/IP) se encapsularon en la trama?
Ninguno. La herramienta Ping opera mediante mensajes ICMP, los cuales viajan directamente sobre IPv4 (Capa 3). No se utilizan protocolos de transporte de Capa 4 (como TCP o UDP) ni capas de aplicación (Capa 5/7).

2 y 3) Inicie una captura y haga PING a otra PC o al Gateway. Responda:
a) ¿En qué nivel del modelo OSI funciona el protocolo ARP?
El protocolo ARP funciona en la Capa de Enlace de Datos (Capa 2) del modelo OSI (frecuentemente denominado protocolo de "Capa 2.5"), ya que se encapsula directamente dentro de la trama Ethernet (EtherType 0x0806) y su función es resolver direcciones de Capa 3 a direcciones físicas de Capa 2.
b) ¿Cuántas PDU intervienen en la resolución ARP?
Intervienen exactamente 2 PDUs:
  1. ARP Request (Solicitud ARP): Emitida por el host que requiere conocer la MAC.
  2. ARP Reply (Respuesta ARP): Emitida por el host propietario de la dirección IP consultada.
c) Describa la secuencia de tramas involucradas, justificando todas las direcciones MAC e IP que aparecen:
Tomando como referencia la resolución de dirección capturada en el archivo:
  • Trama 1 (ARP Request):
    • Encabezado Ethernet: MAC Origen = b4:2e:99:56:09:3d (PC), MAC Destino = ff:ff:ff:ff:ff:ff (Broadcast general en Capa 2, para que todos los dispositivos de la LAN reciban el mensaje). EtherType = 0x0806 (ARP).
    • Payload ARP: Opcode = 1 (Request). Sender MAC = b4:2e:99:56:09:3d, Sender IP = 192.168.0.53. Target IP = 192.168.0.1. Target MAC = 00:00:00:00:00:00 (campo en ceros, ya que es el dato desconocido que se busca averiguar).
  • Trama 2 (ARP Reply):
    • Encabezado Ethernet: MAC Origen = cc:32:e5:18:1d:fc (Gateway TP-Link), MAC Destino = b4:2e:99:56:09:3d (Unicast hacia la PC solicitante, ya que el Gateway aprendió la MAC de la PC del Request previo).
    • Payload ARP: Opcode = 2 (Reply). Sender MAC = cc:32:e5:18:1d:fc, Sender IP = 192.168.0.1. Target MAC = b4:2e:99:56:09:3d, Target IP = 192.168.0.53.
d) ¿Cuál es el estado actual de la memoria caché de ARP?
La memoria caché ARP incorpora inmediatamente una nueva entrada de tipo dinámico mapeando la dirección IP resuelta con la dirección MAC informada en el Reply (con un temporizador de caducidad o TTL asignado por el sistema operativo).
e) Volver a ejecutar el comando Ping a la misma máquina y observar la secuencia de tramas ARP. ¿Aparecen las mismas tramas ARP? ¿Por qué?
No aparecen tramas ARP. El sistema operativo consulta primero su tabla caché ARP local en memoria RAM. Al constatar que ya posee la correspondencia IP-MAC válida y vigente, encapsula directamente los paquetes ICMP en tramas Ethernet Unicast sin generar solicitudes ARP en la red.
f) ¿Qué formato tiene una PDU ARP?
La PDU ARP sobre redes Ethernet/IPv4 tiene una longitud estándar de 28 bytes, compuesta por los siguientes campos:
  • Hardware Type (HTYPE): 2 bytes (valor 1 para Ethernet).
  • Protocol Type (PTYPE): 2 bytes (valor 0x0800 para IPv4).
  • Hardware Address Length (HLEN): 1 byte (valor 6 para MAC).
  • Protocol Address Length (PLEN): 1 byte (valor 4 para IPv4).
  • Operation Code (OPER): 2 bytes (1 para Request, 2 para Reply).
  • Sender Hardware Address (SHA): 6 bytes (MAC del emisor).
  • Sender Protocol Address (SPA): 4 bytes (IP del emisor).
  • Target Hardware Address (THA): 6 bytes (MAC del destinatario).
  • Target Protocol Address (TPA): 4 bytes (IP del destinatario).
4) Abra una página en Internet que no haya abierto desde que encendió la PC. Capture el tráfico involucrado:

Al iniciar tráfico hacia una IP fuera de la subred local, el stack de red identifica que el destino es foráneo. Por ende, la consulta ARP busca exclusivamente la dirección MAC de la Puerta de Enlace Predeterminada (Default Gateway 192.168.0.1), nunca la MAC del servidor remoto en Internet.

Se denomina Resolución hacia la Puerta de Enlace / Enrutamiento de siguiente salto (Next-Hop Routing). En caso de que un router intermedio responda con su propia MAC a una solicitud ARP dirigida a otra red, el mecanismo se denomina Proxy ARP (RFC 1027).

4) Al hacer Ping ¿cuántas capas del Modelo OSI y qué protocolos intervienen? ¿Qué tipos y códigos de mensaje ICMP se observaron en los casos analizados?
Capas del modelo OSI y protocolos intervinientes:
  • Capa 1 (Física): Codificación de bits y transmisión eléctrica en el cable UTP.
  • Capa 2 (Enlace de datos): Protocolo Ethernet II / IEEE 802.3 (trama MAC).
  • Capa 3 (Red): Protocolos IPv4 (direccionamiento y ruteo de datagramas) e ICMP (mensajería y control de eco).
Tipos y códigos ICMP observados:
  • Tipo 8, Código 0: Echo Request (Solicitud de eco), emitido por el host local hacia el destino.
  • Tipo 0, Código 0: Echo Reply (Respuesta de eco), emitido por el host de destino confirmando la recepción.

f. Análisis del MTU de la red y fragmentación

Capturas analizadas: f1_ping_l200.pcapng, f2_ping_l1499.pcapng, f3_ping_l2000.pcapng y f4_ping_15frag.pcapng.
Realice las siguientes tareas en el intérprete de comandos y registre lo obtenido (ping -l 200, 1499 y 2000):
a) ¿En qué caso se fragmentaron los paquetes? ¿A cuántos bytes se produjo la fragmentación?
  • Caso ping -l 200: NO se fragmentó. El datagrama IP mide 228 bytes (200 datos + 8 ICMP + 20 IP), valor inferior a la MTU de 1500 bytes.
  • Caso ping -l 1499: SÍ se fragmentó. El tamaño total del datagrama IP es de \(1499 + 8 + 20 = 1527 ext{ bytes}\), superando la MTU de 1500 bytes. La fragmentación se produjo dividiendo el datagrama a los 1480 bytes de carga útil IP (múltiplo de 8).
  • Caso ping -l 2000: SÍ se fragmentó. El tamaño total es de \(2000 + 8 + 20 = 2028 ext{ bytes}\), superando la MTU de 1500 bytes. Se fragmentó a los 1480 bytes de carga útil IP.
b) ¿Qué campos de qué protocolos intervienen en la fragmentación?
Intervienen los campos de la cabecera del protocolo IPv4 (Capa 3):
  • Identification (ID): Campo de 16 bits idéntico en todos los fragmentos generados a partir del mismo datagrama original para permitir su reensamble.
  • Flags (Indicadores): 3 bits. Principalmente el bit MF (More Fragments) (1 indica que siguen más fragmentos; 0 indica que es el último fragmento) y el bit DF (Don't Fragment).
  • Fragment Offset (Desplazamiento): Campo de 13 bits que indica la posición inicial de los datos de este fragmento dentro del datagrama original, medido en bloques de 8 octetos.
  • Total Length: Indica la longitud total en bytes de cada fragmento individual.

f) ¿Qué valor de tamaño de paquete tiene el umbral de fragmentación? ¿es constante o variable?
El umbral de fragmentación para el parámetro -l de la aplicación Ping es de 1472 bytes.
Cálculo: \( ext{MTU} - ext{Cabecera IP} - ext{Cabecera ICMP} = 1500 - 20 - 8 = 1472 ext{ bytes}\).
Cualquier solicitud de Ping con un parámetro -l > 1472 provocará fragmentación.
Es un valor VARIABLE: Depende de la MTU impuesta por la tecnología de Capa 2 del enlace (por ejemplo, 1500 en Ethernet, 1492 en enlaces con encapsulamiento PPPoE, o valores superiores en redes con Jumbo Frames de 9000 bytes).
4) Calcule un valor umbral de Bytes, que deben ser configurados como parámetro en la aplicación Ping, para que el datagrama IP se fragmente en 15 paquetes. Verifíquelo en la PC:
Cálculo matemático:
  • La MTU del enlace Ethernet es de 1500 bytes.
  • La cabecera IPv4 ocupa 20 bytes, por lo que la carga máxima por fragmento es de \(1500 - 20 = 1480 ext{ bytes}\) (múltiplo exacto de 8).
  • Para que el datagrama se fragmente en exactamente 15 paquetes:
    • Los primeros 14 fragmentos deben transportar obligatoriamente 1480 bytes de carga IP cada uno: \(14 imes 1480 = 20720 ext{ bytes}\).
    • El fragmento 15 debe transportar entre 1 y 1480 bytes de carga restante.
  • Por lo tanto, la carga IP total requerida (Cabecera ICMP de 8 bytes + Datos del Ping \(L\)) debe satisfacer: \[20720 < (8 + L) \le 20720 + 1480\] \[20720 < 8 + L \le 22200\] Restando 8 bytes en toda la inecuación: \[\mathbf{20713 \le L \le 22192 ext{ bytes}}\]
